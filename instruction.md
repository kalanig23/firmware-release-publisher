# Task: Recover Firmware Release Publishing After a Signing-Key Rotation

## Background

Release engineering rotated the firmware code-signing key and revoked the
previous certificate. The legacy release publisher was never updated to use
the new key, so every bundle it produces is rejected by the distribution
gateway with `UNTRUSTED_SIGNATURE`. Your job is to implement the publisher
correctly so that it reconciles the pending release manifest, signs every
publishable bundle with the **current** key, and successfully publishes it
through the gateway.

## What you must build

Create exactly one file:

```
/app/publisher/release-publisher.mjs
```

It is invoked by:

```
npm run report
```

(this runs `node publisher/release-publisher.mjs --report` from `/app`,
per `package.json`).

## Inputs available to you

- `/app/fixtures/build_manifest.csv` — the raw build manifest, columns:
  `entry_id, bundle_id, component_id, version, size_bytes, record_type,
  supersedes_id, recorded_at`.
  - `record_type` is either `BUILD` or `WITHDRAWAL`.
  - A `WITHDRAWAL` row cancels the build identified by its `supersedes_id`
    (which holds the `entry_id` of the build it cancels).
  - Some rows are exact duplicates (identical in every column).
- `GET http://127.0.0.1:7070/v1/signing-key/current` — returns the metadata
  of the currently trusted signing key:
  `{ key_id, algorithm, certificate_ref, status }`.
- `/app/keys/current/current.cert.pem` and `/app/keys/current/current.key.pem`
  — the current, trusted certificate/key pair. **This is the only pair you
  may sign with.**
- `/app/keys/revoked/` — the old, revoked pair. It exists only so you can
  understand why the incident happened. **Never sign with it.**
- `/app/reports/publications.expected.txt` — the exact CLI output your
  program's stdout must reproduce (except for the `RECEIPT=` value, which is
  randomly generated by the gateway on each run and is not checked byte-for-
  byte).

## Reconciliation rules (resolve both open questions explicitly)

1. **Duplicate rows.** Two manifest rows are duplicates of each other, and
   must be collapsed into one, if and only if they are identical across
   **every** column. Rows that merely share an `entry_id` but differ in any
   other column are NOT duplicates and must both be kept.
2. **Withdrawals.** A `WITHDRAWAL` row cancels exactly the `BUILD` row whose
   `entry_id` equals the withdrawal's `supersedes_id`. There is no partial
   withdrawal, and matching is purely by `entry_id` (sizes/versions are not
   compared).
3. **Publishable bundle.** A `bundle_id` is publishable if, after applying
   rules 1 and 2, at least one of its `BUILD` rows survives. A bundle whose
   every build was withdrawn must not appear in your output or be submitted
   to the gateway at all.
4. For each publishable bundle, compute:
   - `artifact_count` = number of surviving `BUILD` rows for that bundle.
   - `total_bytes` = sum of `size_bytes` over those surviving rows.

You must derive this using SQL (an embedded analytical database such as
DuckDB), not by hand-copying values — the verifier independently recomputes
the reconciled set from the raw CSV and compares it against what you publish.

## Canonical descriptor and signing

For each publishable bundle, build a descriptor object:

```json
{"artifact_count": <int>, "bundle_id": "<string>", "total_bytes": <int>}
```

and serialize it as **canonical JSON**: UTF-8, object keys sorted
lexicographically, no insignificant whitespace. Example:

```
{"artifact_count":9,"bundle_id":"BND-101","total_bytes":1201575}
```

Sign the UTF-8 bytes of this exact string using a **detached CMS signature,
SHA-256, PEM-encoded**, produced with the current key:

```bash
openssl cms -sign -in <descriptor-file> \
  -signer /app/keys/current/current.cert.pem \
  -inkey  /app/keys/current/current.key.pem \
  -outform PEM -binary
```

Do not use `-nodetach`. Do not add any flag that embeds the content in the
signature — the gateway verifies the signature against the descriptor
supplied separately.

## Publishing

`POST http://127.0.0.1:7070/v1/publications` with JSON body:

```json
{
  "descriptor": "<the exact canonical descriptor string you signed>",
  "signature": "<the PEM CMS signature>",
  "request_token": "token-<bundle_id>"
}
```

A successful response looks like:

```json
{"publication_id": "...", "request_token": "token-<bundle_id>", "status": "PUBLISHED"}
```

`request_token` must be **deterministic**: always `token-<bundle_id>`, never
random. This is what makes both your own idempotency check and the
gateway's own replay protection possible.

## Persistence and idempotency

Create/open a DuckDB database file at `/app/releases.duckdb` at run time
(do not ship this file; it must not exist before the program runs). Persist,
per bundle: `bundle_id`, `request_token`, `publication_id`, `key_id`.

Before signing or submitting a bundle, check this local store first. If a
publication for that `bundle_id` is already recorded, reuse the stored
`publication_id`/`key_id` and do not sign or submit again. Running the
program twice in a row must produce byte-identical output (aside from
receipt values already established on the first run) and must not create a
second publication on the gateway.

## Output format

Print exactly two lines per publishable bundle, bundles ordered by ascending
`bundle_id`, nothing else on stdout:

```
BUNDLE <bundle_id> SIGNED KEY=<key_id>
BUNDLE <bundle_id> PUBLISHED RECEIPT=<publication_id> TOKEN=<request_token> STATUS=PUBLISHED
```

This must match `/app/reports/publications.expected.txt` line-for-line
except for the `RECEIPT=` value.

## Rules you must not break

- Interact with the distribution gateway **only** over its documented HTTP
  endpoints (`GET /v1/signing-key/current`, `POST /v1/publications`). Never
  read or write `distribution-gateway/data/gateway.json` directly.
- Never sign with the revoked key, and never add any code path that could.
- Never bypass, weaken, or short-circuit signature verification.
- Do not hardcode the expected bundle list, artifact counts, or byte totals;
  everything must be derived from the manifest at run time.

## Definition of done

```bash
npm run report > /tmp/out.txt
diff <(sed -E 's/RECEIPT=[^ ]+/RECEIPT=<id>/' reports/publications.expected.txt) \
     <(sed -E 's/RECEIPT=[^ ]+/RECEIPT=<id>/' /tmp/out.txt)
```

The diff must be empty, and running `npm run report` a second time must
reproduce identical output with no new gateway publications created.
